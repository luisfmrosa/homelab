## Configuration files

* `src/opentofu/providers.tf` — declares the `lxc/incus` provider, targeting the `homelab` remote already trusted via the laptop's Incus client config (`references/INSTALL.md`). No separate provider-side login needed.
* `src/opentofu/variables.tf` — `ssh_user` / `ssh_public_key` variables, filled in via `terraform.tfvars` (gitignored; copy `terraform.tfvars.example` and fill in the real values).
* `src/opentofu/naspool.tf` — the `naspool-samba` LXC instance (`images:debian/12`), autostarted (`boot.autostart = true`), with the host's `/naspool` bind-mounted to `/naspool` via a `disk` device. Named `naspool-samba` rather than `naspool` to disambiguate it from the host's `/naspool` BTRFS mount itself and the (planned) `naspool-buckets` Incus storage pool for S3 buckets — `naspool` alone had become ambiguous across all three. No cloud-init provisioning (unlike an earlier version of this file) — Ansible connects via `incus exec` instead of SSH (see `references/ANSIBLE.md`), same as `headscale.tf`'s instance, so there's no need for a provisioned user/SSH key. Networked on the default NAT'd `incusbr0` bridge; exposed to the LAN and tailnet via a `proxy` device forwarding `445/tcp` (SMB) from the homelab host's own addresses to the container's loopback — same pattern as `headscale.tf`'s proxy devices, and the same reasoning as the Incus web UI's tailnet reachability (`tailscale.yml`): both the host's LAN IP and its tailnet IP terminate on the host itself, so one proxy device covers both. No NFS proxy device — the kernel NFS server can't run inside this (deliberately unprivileged) container, since it needs to mount `/proc/fs/nfsd`, which Incus denies unprivileged containers as a host-kernel isolation boundary; confirmed in practice (`mount: /proc/fs/nfsd: permission denied`) rather than assumed. Samba alone covers the actual use case, so NFS was dropped instead of making the container privileged.
  * This supersedes the `src/incus-compose/naspool.yaml` approach: incus-compose refuses bind mounts over a remote (HTTPS) connection as a client-side safety check ("not on the same host"), since bind-mount source paths are only meaningful read from the host actually running the Incus daemon. OpenTofu's `lxc/incus` provider has no such client-side guard — a `disk` device's `source` is resolved by the Incus daemon on the homelab regardless of which machine issues the API call, so it works fine from the laptop over HTTPS. See `references/INCUS-COMPOSE.md` for that background.
* `src/opentofu/naspool-buckets.tf` — an `incus_storage_pool` (BTRFS driver, source `/naspool/incus-buckets`), an `incus_storage_bucket` named `incus-bucket` on that pool, and an `incus_storage_bucket_key` for read-write (`admin` role) S3 access. The `incus_storage_bucket_key` resource was imported from the `admin` key Incus auto-creates for every new bucket, rather than created fresh, since a declared key named `admin` collides with Incus's own. Requires `core.storage_buckets_address` to be set on the Incus server (`incus.yml`) for the bucket to actually be reachable over S3 — without it the bucket exists but nothing can connect. `access_key`/`secret_key` are stored in plain text in Terraform state (a documented provider limitation) — treat the state file as a secret, same as `terraform.tfvars`.
* `src/opentofu/headscale.tf` — the `headscale` LXC instance (`images:debian/12`), autostarted. No cloud-init provisioning (unlike `naspool.tf`) — Ansible connects via `incus exec` instead of SSH (see `references/ANSIBLE.md`), so there's no need for a provisioned user/SSH key. Networked on the default NAT'd `incusbr0` bridge, **not** a `macvlan` NIC on the homelab's physical `wlo1` — a macvlan was tried first so the container could get its own IPv6 directly from the router, but macvlan doesn't work reliably over WiFi (confirmed in practice: the container had a global IPv6 and a default route, but zero actual reachability — WiFi access points generally only accept traffic for the one MAC they associated with, silently dropping frames from a second virtual MAC riding the same radio). Instead, three `proxy` devices forward `443/tcp`, `80/tcp`, and `3478/udp` from the **homelab host's own** address (which has real, working WiFi connectivity) to the container's internal `127.0.0.1` — see the "headscale" section in `references/INSTALL.md` for the router firewall rule, which now points at the homelab host itself rather than the container. See `references/ANSIBLE.md` for the Caddy + headscale configuration layered on top.
* `src/opentofu/immich.tf` — isolation for the Immich photo management stack: an `incus_project` named `immich`, and a dedicated `incus_network` bridge (`immich-br0`) the project is restricted to via `restricted.networks.access` (bridge networks can't themselves live inside a non-default project — only OVN can — so `immich-br0` sits in the `default` project like `incusbr0`, and isolation is enforced at the project-restriction layer instead). The project also sets `restricted.devices.disk = "allow"` + `restricted.devices.disk.paths = "/naspool/immich"` (restricted projects default to pool-backed-only disks, blocking the plain bind mounts Immich's containers need) and `restricted.devices.proxy = "allow"` (restricted projects block proxy devices outright, needed for exposing the web UI). An explicit `incus_profile` (`immich_default`) is declared for the project too — enabling `restricted` requires `features.profiles = true` first, which otherwise makes Incus copy the **default** project's own default profile (`eth0` → `incusbr0`) verbatim into the new project, immediately conflicting with the network restriction; applied in two passes the first time (profiles enabled, profile fixed; then restriction flags added) — see the file's own comments for the exact sequencing. The 4 Immich services themselves are **not** `incus_instance` resources here — they're Incus OCI "application containers" (`incus launch docker:...`/`ghcr:...`), and the `lxc/incus` Terraform provider has an open bug ([lxc/terraform-provider-incus#348](https://github.com/lxc/terraform-provider-incus/issues/348)) breaking OCI image/remote resolution for that resource type — so instance creation, their disk/proxy devices, and startup all live in `src/ansible/playbooks/immich.yml` instead (see `references/ANSIBLE.md`).
* `src/opentofu/media.tf` — isolation for the media stack (Jellyfin, Navidrome, Kavita), structurally identical to `immich.tf`: an `incus_project` named `media`, a dedicated `incus_network` bridge (`media-br0`, `10.10.20.0/24` — Immich's is `10.10.10.0/24`), and an explicit `incus_profile` for the project's own `default` (eth0 → `media-br0`). Unlike Immich's 4 services, these three never communicate with each other at all — they're one project because they share a trust domain, a data source and an audience, not because they need a common L2. Two differences from `immich.tf`'s restriction set:
  * `restricted.devices.disk.paths` lists **two** prefixes rather than one: `/naspool/biblioteca` (the pre-existing media library, mounted **read-only** — see `media.yml`) and `/naspool/media` (writable config/cache/database for the three services). Keeping them separate is what guarantees a service can never write into the archive it indexes; Samba (`naspool-samba`) stays the only writer to `/naspool/biblioteca`.
  * `restricted.devices.gpu = "allow"` — **not present on the immich project**. Restricted projects default this to `block`, so without it Jellyfin's `gpu` device fails to attach at all. It's a deliberately broader grant than the disk/proxy ones: Incus has no `restricted.devices.gpu.*` allowlist, so it permits any GPU device in the project rather than only Jellyfin's `renderD128`. Accepted because this homelab's CPU (Intel Pentium Silver J5005, Gemini Lake, 4 weak cores) cannot realistically software-transcode even a single 1080p stream — QuickSync is what makes Jellyfin viable here at all.
  * Applied cleanly in a **single** pass, unlike `immich.tf`'s documented two-pass first apply — the provider still emits the same benign `Default Profile Creation Attempted` warning, but the profile/restriction conflict didn't materialize this time. The two-pass fallback is still noted in the file's own comments in case a from-scratch re-apply hits it.
* Run with (from `src/opentofu/`): `tofu init`, `tofu plan`, `tofu apply`. See `references/INSTALL.md` for one-time laptop setup (installing `tofu` itself).
* After creating an SSH-reachable instance, find its IP with `incus list` and add it as a new Ansible host (`src/ansible/hosts`) with `ansible_host=<ip>`. Instances managed via the `community.general.incus` connection plugin instead (like `headscale` and `naspool-samba`) don't need an IP in the inventory — just `ansible_incus_host=<instance-name>`.
